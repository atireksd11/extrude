# Learning rule

More runs of the current loop do not create motherboard skill. The loop repairs misses the checkers already know how to name. A rule that is not in the checkers is invisible, so the model can be right in prose and still fail the board.

`extrude/learn` stays unloaded on `POST /v1/design` and on `walk`. `propose_offline` keeps raising `NotImplementedError` through week 10.

## What a retry is

A retry is a second proposal in the same process, after a `MUST_FIX` payload. It can raise the score on tasks whose checks exist. It cannot invent DDR training, plane impedance, or a fab defect that no checker measures.

## What may be stored

A row in `constraints` after a checker fails. That is retrieval for the next similar card. It is not a weight update.

A trajectory worth keeping for any future training file is:

1. The frozen card.
2. The proposal.
3. The checker log.
4. The repair proposal.
5. A final status of `checked` from the same checkers, including DRC when the task has a board.

If step 5 is missing, the trajectory is discarded. A strong model’s answer is not an exception. Sol and Opus traces follow the same rule.

## When weights would even be discussed

All of these are true at once:

- The slice pack has two harness-on runs and the practice eight did not regress.
- Failed trajectories were excluded by the rule above.
- A replay of the frozen packs, with no weight change, is the baseline.
- A later offline experiment beats that baseline on the same packs without dropping a task.

Until then, the harness is the moat: new checkers, sharper payloads, and datasheet tables. Training is a later project that consumes this harness’s pass logs. It is not how week 8 reaches 80%.

## Reward shape, parked

If an offline experiment is ever run, the reward is lexical:

1. Technical pass, including no power-to-ground short, is required.
2. Only then does cost efficiency matter, using the existing blend.
3. Board area is not a reward in this program.

There is no partial credit for a short.
